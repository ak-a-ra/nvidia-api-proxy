# Task brief — e04s01 / task 5: the buffered-body ceiling and the per-model limits map

> Source of requirements: `specs/epics/e04-rate-limiting/e04s01-tasks.yaml` task 5,
> `specs/epics/e04-rate-limiting/e04s01-config-owner-and-bind-host.md` §2 (ADDED blocks),
> §8 (interfaces table), §12 (failure modes), §13 (security), §17 (Gherkin), plus the decisions
> already recorded in `specs/state.yaml` and `LOG.md`. Where this brief and the story disagree,
> the story wins and the deviation is reported — do not silently pick one.

## Objective

`config.js` grows two more operators' settings:

- `PROXY_MAX_BUFFERED_BODY_BYTES` — a scalar ceiling, default 8 MiB, fatal on invalid.
- `PROXY_MODEL_LIMITS_JSON` — a JSON object keyed by exact case-sensitive model ID, each entry
  supplying a positive integer `rpm`, `tpm`, or both. Fatal whenever the variable is supplied
  and the value is malformed, and **never partially applied**.

Neither is acted on. Both are validated and stored, like every other operational variable in
this story. Admission control, request buffering, and budget enforcement are later slices.

## Requirements

1. **`PROXY_MAX_BUFFERED_BODY_BYTES` uses the existing integer guard, unmodified.** Default
   8388608 (8 MiB = 8 × 1024 × 1024). Blank or absent → default. A supplied value must be a
   positive safe integer in plain decimal digits, the same rule the rate pair and the four
   limit variables already use. `0` is fatal, for the reason in requirement 2's sibling: a
   zero-byte buffer rejects every request body, a limit that appears to exist and does not.
   Store it in the existing `limits` object as `maxBufferedBodyBytes` — it is a ceiling, the
   same kind of member as `maxQueueSize`, not a group of its own.

2. **`PROXY_MODEL_LIMITS_JSON` is a new top-level nullable field, parallel to `rateLimit`.**
   Absent or blank → `null`. Supplied → the parsed, validated map. Do not put it in `limits`:
   `limits` holds scalar ceilings, this holds a map of budgets, and the story's own glossary
   separates "Rate budget" from "Per-model budget". A caller must not be able to read a
   per-model budget map beside a half-configured global rate pair.

3. **Fatal whenever supplied and malformed. The five named shapes, plus two the story's own
   principle covers.** All of these exit 1 and name `PROXY_MODEL_LIMITS_JSON`:

   | Supplied value | Why it is fatal |
   | --- | --- |
   | `{not json` | bad JSON |
   | `null`, `[]`, `"a"`, `5`, `true` | non-object root |
   | `{"": {"rpm": 5}}` | empty model key |
   | `{"gpt": 5}`, `{"gpt": null}`, `{"gpt": []}`, `{"gpt": "x"}` | non-object entry |
   | `{"gpt": {"rpm": 0}}`, `{"gpt": {"rpm": -1}}`, `{"gpt": {"rpm": 1.5}}`, `{"gpt": {"rpm": "60"}}`, `{"gpt": {"rpm": true}}`, `{"gpt": {"rpm": 1e30}}` | invalid rpm/tpm value |
   | `{"gpt": {}}` | entry supplies neither `rpm` nor `tpm` |
   | `{"gpt": {"rps": 5}}` | unknown key silently dropped |

   Rows 6 and 7 are not in the story's enumerated list, but the story states the rule they come
   from twice — "never partially applied — a silently dropped model limit is a budget that
   appears to exist and does not" (§2) and "a partially applied `PROXY_MODEL_LIMITS_JSON` fails
   open. Reject the whole value" (§12). An entry with no budget, and a key name the operator
   misspelled, are both silently dropped budgets. The decision is recorded in
   `specs/state.yaml`; implement it, and report it as a scope judgment in the report.

4. **One reject, not per-row reporting.** The variable is fatal as a whole. The first
   malformed entry ends the process. There is no "collect all problems" mode and no partial
   acceptance of the entries that happened to be valid.

5. **No `try { … } catch {}` anywhere on this path, and no `catch` that swallows and
   continues.** A `JSON.parse` failure must be fatal. This is also checked by the verify
   command's own regex (`/catch\s*\{\s*\}/`), so do not write an empty catch block even for a
   case you think is unreachable. `config.js` already has a non-empty `catch` for the base
   URL, which is fine.

6. **Model keys are stored exactly as written, and are never trimmed, lowercased, or
   otherwise normalized** — the story says "exact case-sensitive model ID". A key that is not
   equal to its own trimmed form (`" gpt "`) is fatal: it can never match a model ID, so it is
   a budget that appears to exist and does not. A key that is empty after trimming is the
   "empty model key" case above. The stored map's keys are the JSON's keys, byte for byte.

7. **Reuse the single integer guard for the per-model numbers — do not write a second
   numeric guard, and do not call `Number()` on the value.** The scalar guard
   `readPositiveInteger` is text-based (it rejects `1e3`, `0x10`, `+5`, `1_000`), and
   `JSON.parse` has already normalized the text away by the time you hold the value. So:

   ```js
   // type first, then the one guard
   if (typeof value !== "number") fatal(name, …);        // catches "60", true, null
   readPositiveInteger(`PROXY_MODEL_LIMITS_JSON["gpt"].rpm`, String(value));
   ```

   The `typeof` check must come first, or a quoted number (`{"rpm":"60"}`) would be accepted
   because `String("60")` is `"60"`. The guard is reused with `String(value)` because after
   the type check that is exact: a JSON number is a JS number, `String()` round-trips it
   unambiguously, and the guard's own `Number.isSafeInteger` check then rejects `1e30`. Say
   this in a comment — the next reader will otherwise think `String()` reintroduces the
   coercion problem the guard exists to prevent. Note the asymmetry honestly: the
   scientific-notation rejection applies to env scalars only, because JSON's numeric grammar
   accepts `1e3` and produces `1000`; by the time the value exists there is no textual
   evidence of what the operator wrote.

8. **Every fatal message names the variable and the offending location.** For a bad entry the
   operator needs to find it in a possibly large document: name the model key and the field,
   e.g. `PROXY_MODEL_LIMITS_JSON["gpt-4o-mini"].rpm must be a positive integer, got: 1.5`.
   For bad JSON, name the variable and let the parser's own message carry the position. **Do
   not echo the whole document** into stderr — it can be large and it is operator-supplied
   input. This does not weaken the existing convention of echoing the offending scalar value,
   which applies to the env-var guards.

9. **Blank beats parsing, in the same order the other groups use.** `Boolean(raw?.trim())`
   decides whether the variable was supplied at all, *before* any `JSON.parse`. A
   whitespace-only value must reach the default, not the parser — `JSON.parse("  ")` throws,
   and a blank value that crashes startup is exactly the silent-rewrite failure the story
   names in §12. The blank check must precede numeric parsing for the same reason, and that
   ordering is what task 6's verify looks for.

10. **`readPositiveInteger`'s signature does not change and neither does `integerRule`'s
    wording for any existing variable.** `PROXY_MAX_BUFFERED_BODY_BYTES` uses the default
    bounds, so its message is `PROXY_MAX_BUFFERED_BODY_BYTES must be a positive integer, got:
    1e3`, and `PROXY_MODEL_LIMITS_JSON["gpt"].rpm` reads the same way. The rate pair's and the
    four limit variables' messages stay byte-identical — tests assert their exact text.

### Decisions already made — implement them, do not re-open them

- Extend the single decimal-digits-only integer guard rather than write a second one. The
  `min`/`max`/`zeroDisables` bounds already added for task 4 exist for exactly this reuse.
- One field per coherent group: `rateLimit`, then `limits` for the scalar ceilings, then a
  new top-level `modelLimits` for the budget map. No loose top-level keys.
- Anything a later slice will distinguish needs a test today, because the config object itself
  is invisible to the harness. Later slices enforce rate budgets, per-model budgets, and the
  body ceiling; they will need to tell "unset" from "defaulted" from "explicitly 0".
- Test names for this task must **not** contain the word `whitespace`. Task 6's verify filters
  on that word and requires a hit naming one of task 4's four variables; task 4 deliberately
  left the word out so task 6's gate stays falsifiable. Use `blank` instead, as task 4 did.

## The tests

Append a new `describe` block after the existing `operational limit config` block. Both harness
seams already exist — `runProxyOnce` for the fatal cases (pass a valid `NVIDIA_BASE_URL` and
both credentials, so an exit 1 proves *your* guard and not an unrelated missing variable) and
`withProxy` for the cases that must start. Every new test that starts the proxy must pass the
variable as `undefined` when it means "absent", because `withProxy` merges `proxyEnv` over
`process.env` and passing nothing pins the author's shell instead of absence.

Required areas — all of them:

1. Both variables absent (`undefined`) → starts, `/health` 200.
2. Both blank (`""`, `"   "`, `" \t "`) → starts, `/health` 200. For
   `PROXY_MODEL_LIMITS_JSON` a blank value must not reach `JSON.parse`; if it did, it would
   throw and the process would exit 1.
3. `PROXY_MAX_BUFFERED_BODY_BYTES` valid values start and proxy normally, including the
   boundary values: `1` and a large safe integer. Include one pass-through request, so the
   test proves validation does not disturb request handling.
4. `PROXY_MAX_BUFFERED_BODY_BYTES` invalid values exit 1, naming the variable *and* stating
   the rule: the negative, fraction, non-numeric, unsafe-integer, scientific, hex,
   explicitly-signed, leading-dot, digit-separator and 30-digit-run values the task 4 block
   already uses, plus `0`. Reuse a table in the shape task 4's `LIMIT_VARIABLES` /
   `INVALID_VALUES` tables use, or extract nothing — do not modify task 4's tables.
5. `PROXY_MAX_BUFFERED_BODY_BYTES` at exactly `0` is fatal, and the message must not imply `0`
   is usable. If the message is asserted, assert the whole `must be a positive integer` text.
6. `PROXY_MODEL_LIMITS_JSON` with well-formed limits starts and proxies normally: one entry
   with both fields, one with only `rpm`, one with only `tpm`, and the empty object `{}`
   (valid, zero models). This is what proves "validated, not applied" and that nothing is
   rejected for being generous.
7. Each fatal shape in requirement 3's table exits 1, and stderr names
   `PROXY_MODEL_LIMITS_JSON`. For a bad entry, also assert the message names the model key or
   the field, so the operator can locate the problem.
8. Never partially applied: one value containing **both** a valid and an invalid entry exits 1,
   proving the valid half was not adopted. The harness cannot observe the stored map, so this
   test is the observable half of that requirement — the process must not come up.
9. Model keys are case-sensitive and unnormalized: two entries differing only in case
   (`{"Gpt":{"rpm":5},"gpt":{"rpm":6}}`) start normally, and a key with surrounding spaces
   exits 1.
10. The whole suite must stay green at 56 + the new tests, and `server.test.js` must be
    **additive only** — zero deletions, zero modifications, zero reorderings. A later slice
    needs those tests as its contract.
