## Requirements (from the task ledger, task id 2)

1. `createBudget` accepts a third argument `modelLimits` (the config map or `null`).
2. When `modelLimits` is non-null **and** the global `rateLimit` is non-null, one window pair per
   model entry is built at construction time, using the same `effectiveLimit` arithmetic and the
   same `safetyMarginPct` as the global windows.
3. A model entry may supply only `rpm`, only `tpm`, or both. The missing dimension is uncapped for
   that model: no window for it.
4. The effective model limits are exposed as `modelEffective` on the returned object: a map of
   `{ [model]: { rpm?, tpm? } }`, or `null` when there are no model windows.
5. `close()` closes all model windows alongside the global windows.
6. A `null` `modelLimits`, or a disabled global budget (`rateLimit` null), creates no model
   windows.
7. Tests: `createBudget` with `modelLimits` builds the model effective limits, and `close` refuses
   model reservations.

## Orchestrator decisions (apply these; record any deviation in the report)

### D4 — model windows are built at construction time

The story contradicted itself; §2 said "created lazily on first reservation for that model" while
§5 step 2, §6 ("No lazy window creation") and the ledger's task 2 all say construction time. §2
was amended to match, and construction time wins: the map is bounded by the operator's config, and
lazy creation would reintroduce the race between the first two requests for a model that §6 rules
out. The story's §11 invariants and §17 scenarios follow from construction time.

### D5 — `modelEffective` and the internal model-window map are null-prototype maps

A model ID is operator-supplied text. On a normal object, a key like `__proto__` is swallowed by
the prototype setter, so that model's budget would silently disappear — the same failure class
`config.js` already guards against (see its `PROXY_MODEL_LIMITS_JSON` parsing: "a key like
`__proto__` would be swallowed by the prototype setter … an entry that silently disappears").

Therefore:

- `modelEffective` is created with `Object.create(null)`.
- The internal map of model windows is created with `Object.create(null)`.
- The inner entry objects (`{ rpm?, tpm? }`) are plain objects: their key set is fixed at `rpm` and
  `tpm`, so no operator text ever becomes a key.

`config.js` already hands over a null-prototype map; the budget keeps that property all the way
through.

### D6 — `createBudget`'s returned shape is uniform

`modelEffective` is present on the returned object in both cases: the enabled gate (`null` when no
model windows exist) and the disabled gate (`rateLimit` null → `modelEffective: null`). The
story's §8 interface lists `modelEffective` in the returned object, so a caller can read it
without knowing which gate it got.

### D7 — `reserve()` does not change in this task

The model windows are built and closed, but `reserve()` keeps deciding exactly as it did after
task 1: the global windows only. A request naming a configured model is still admitted by the
global budget in this task. Do **not** write a test that pins that intermediate behavior — task 3
changes it, and a test written here would have to be flipped rather than added. Pin the global
behavior instead (see test 6 below).

### D8 — the ledger's verify command is vacuous; strengthen it as task 1 did

The ledger's task-2 verify is `node --test --test-reporter=tap --test-name-pattern 'per-model
windows are built|close refuses model' server.test.js` followed by a grep for
`^[[:space:]]*ok [0-9]+ -`. Measured on this tree (2026-10-21): a pattern that matches no test
still exits 0 and prints the file-level line `ok 1 - server.test.js`, which that grep matches. Use
the name-counting form instead:

```bash
out=$(node --test --test-reporter=tap --test-name-pattern 'per-model windows are built|close refuses model' server.test.js 2>&1); rc=$?; test "$rc" -eq 0 || { printf '%s\n' "$out"; exit "$rc"; }; n=$(printf '%s\n' "$out" | grep -cE '^[[:space:]]*ok [0-9]+ - .*(per-model windows are built|close refuses model)'); test "$n" -ge 2
```

Replace **only** task 2's `verify` string in `e04s05-tasks.yaml` with this, keep the row's
`status: failing` until it exits 0, and record the change in the report. Do not touch the other
rows and do not touch the story-level `status`.

### D9 — one window implementation, shared by the global gate and the model windows

The global gate and the model windows must agree on the 60-second horizon, the pruning rule, the
effective-limit arithmetic, and how a `Retry-After` is derived. Prefer a small internal factory
that both use, so they cannot drift. If you instead give the model windows their own
implementation, the report must justify the duplication.

Whatever you choose, the global gate's observable behavior must not change: the e04s04 tests must
stay green exactly as they are.

## Implementation notes

- `modelEffective` reports the **effective** limits (after the safety margin), not the raw
  configured numbers. A dimension with no window is absent from the entry, not `null` and not
  `undefined`-valued.
- The margin source stays the one the global windows use (`limits?.safetyMarginPct ?? 5`), so the
  two cannot disagree about the margin.
- The model ID is used as a map key exactly as `config.js` stored it. No trimming, no
  case-folding, no normalization. A client whose model ID differs from the config key simply
  matches no window (task 3 makes that fall through to the global budget).
- Every model window must be independent: its own event history, its own effective limits, its
  own closed flag.
- Keep the module's comment voice: explain the constraint, not the mechanics. Explain *why* the
  model map is null-prototype and why the windows are built up front.
