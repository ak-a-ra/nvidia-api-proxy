## Zoom-out checks (mandated)

### `config.js` — purpose, callers, contracts

- **Purpose**: single source of truth. One `parseConfig(env)` validates every variable, is the only owner of defaults and parsing.
- **Callers**: `server.js` (module import), `server.test.js` (child spawn).
- **Contracts**: `rateLimit` = `null` (disabled) or `{rpm, tpm}`; `limits` = `{maxConcurrentRequests, maxQueueSize, queueTimeoutSeconds, safetyMarginPct, maxBufferedBodyBytes}`; `modelLimits` = null or null-prototype map. Fatal regime: exit 1 for base URL and every operational variable problem.

### `admission.js` — purpose, callers, contracts

- **Purpose**: concurrency ceiling + bounded FIFO queue + abort-aware cancellation + shutdown close. Knowledge: concurrency only.
- **Callers**: `server.js` only (`createAdmission`, `acquire`, `close`, `REJECTION_REASONS`).
- **Contracts**: `createAdmission(limits)` → `{acquire(signal), close()}`; `acquire` resolves ticket `{admitted, reason, release}`; `close()` sync, idempotent. No estimation, no budget knowledge. **Do not modify `admission.js` in this story.**

### `server.js` — purpose, callers, contracts

- **Purpose**: HTTP entry. Bind, route, auth, admission gate, proxy forward, response copy, SIGTERM drain.
- **Callers**: node (`npm start`), `server.test.js` (child spawn with per-test env).
- **Contracts**: request handler order is auth (401) → unconfigured (503) → local endpoints (`/health` 200 unconfigured 503, else 404) → admission acquire (429 on rejection) → proxy handler → response. `sendJson(req, res, status, body, extraHeaders)` drains the request first so keep-alive survives early rejections.
- **Enforcement must not break the streaming no-buffer path when rate limiting is disabled.**

### New root module — estimate + rolling budget

Epic decision in `specs/state.yaml`: "e04s01 extracts config.js only; the deep-module split is deferred … issue #13 user stories 135-138 describe deep internal modules (limiter, queue, reconciliation) distinct from a server entry, but they belong to e04s02-e04s09, not to issue #14." So this story lands a new root module for estimation + rolling budgets, alongside `admission.js`. Name it `budget.js` unless a stronger name is found during exploration; justify in the report.

- **Purpose**: rolling 60-second RPM/TPM windows, Safety margin arithmetic, cost estimation from buffered metadata, byte-cap enforcement.
- **Callers**: `server.js` only.
- **Contracts**: validated inputs come from `config.js`. `budget.js` re-reads no environment, carries no fallback default. A caller must not be able to read a half-configured budget.

## Requirements, verbatim from issue #17

Acceptance criteria, all must pass:

1. Both rate variables absent or blank disables rate limiting and preserves the fully streaming no-buffer path; exactly one nonblank variable remains fatal.
2. Global RPM and TPM use rolling 60-second windows; RPM counts each admitted request once and TPM reserves estimated cost before Upstream contact.
3. The Safety margin defaults to 5, accepts integers 0 through 50, and computes every effective limit as `max(1, floor(limit * (1 - margin / 100)))`.
4. With rate limiting enabled, request bodies are buffered only to extract metadata, estimate cost, and enforce `PROXY_MAX_BUFFERED_BODY_BYTES`, which defaults to 8,388,608 bytes.
5. Ordinary JSON, non-canonical JSON, Unicode, malformed JSON, and content-encoded bodies are forwarded byte-identically with original headers intact.
6. Gzip, encoded, malformed, non-JSON, unknown-model, and no-model bodies use the global budget with a four-characters-per-token byte estimate rounded up and a minimum cost of one token.
7. The estimator covers message content, tool definitions, and requested output; requested output defaults to 1,024 tokens and is capped at 4,096.
8. A body above the cap receives status 413 with exact body `{ "error": "Request too large" }`, never reaches the Upstream, and leaves the proxy usable.
9. Estimated cost above the effective global TPM receives an immediate status 429 with exact generic body and positive `Retry-After`, never queues, and never reaches the Upstream.
10. Waiting for budget is event-driven only: no polling. Blocking budget waits respect downstream client disconnect.

## Testing plan

Mirror the existing style. Use `describe("e04s04 ...")` as a new block appended with the other rate/admission blocks. Add stub modes only if a scenario cannot be expressed with existing ones; every new mode must be documented in the test file.

Scenarios to cover, one test each minimum:

Disabled mode:

- both RPM and TPM absent → streaming requests work, buffering never engaged (byte-identical body, no 413 regardless of size under cap default), upstream receives stream.
- exactly one nonblank → fatal exit 1 (child never reports ready; exit code non-zero).

Margin arithmetic:

- effective limit values for margin 0, 5, 50 across boundary integers, including `max(1, floor(...))` floor-to-1 cases. Test through observable behavior where possible, or unit-test the exported arithmetic if it is pure. Prefer black-box through the server: set tight budgets and observe 200 vs 429.

Rolling windows:

- RPM counted once per admitted request even when the request body is large.
- TPM reserved before upstream contact: a request that would exceed TPM never reaches upstream (stub must record zero hits), returns 429.
- window rollover: costs expire at 60s. Do not test a full 60-second wait; instead assert the window is a rolling window of bounded event history by unit-testing the exported window structure if exported pure, or by driving a small number of requests and observing that capacity is bounded, plus one focused test that a pruned event changes the held total.

Estimator:

- ordinary JSON with messages + tools + `max_tokens` (or `max_completion_tokens` / tool choice output fields present) is estimated from content plus requested output, default 1024 when absent, capped 4096.
- non-canonical JSON (extra whitespace, key order) same cost as canonical equivalent.
- Unicode content counted by characters per the documented rule (state the chosen rule explicitly in the report: byte length vs code point count; the AC says "four-characters-per-token byte estimate", so the fallback uses byte length; for JSON the estimator's own rule must be stated and tested).
- malformed JSON → fallback estimator, min 1 token.
- non-JSON → fallback estimator.
- unknown-model and no-model bodies → global budget with fallback estimate.

Buffering and cap:

- rate limiting enabled + body above `PROXY_MAX_BUFFERED_BODY_BYTES` → 413 with exact body `{ "error": "Request too large" }`, stub records zero hits, subsequent request 200 (proxy usable).
- byte-identical forwarding with original headers intact for ordinary JSON, non-canonical JSON, Unicode, malformed JSON, content-encoded bodies.
- gzip (and other encoded) bodies: fallback estimate; forwarded byte-identically. This requires the test to compress and send with original `content-encoding` header preserved (see `zlib` already imported in `server.test.js`).
- disabled mode never buffers, so a body above the cap is forwarded as a stream, no 413.

429 arm:

- estimated cost above effective TPM → 429 with a generic exact body and positive `Retry-After` header; never queues (no admission interaction required to reject); stub zero hits.
- 429 body must not leak internals.

Event-driven wait + disconnect:

- budget exhaustion causes a wait that resolves when budget frees; client disconnect during the wait cancels it with no upstream call and no resource leak. Assert the proxy stays usable afterwards.
- no polling: the story asserts event-driven only. If the implementation uses a timer, justify it in the report as an event (timer-driven), not a poll.

Per-model limits are validated but NOT enforced in this story — a body with a model key present still uses the global budget. Add one test asserting per-model JSON is accepted and does not change global behavior (documenting the slice boundary).
