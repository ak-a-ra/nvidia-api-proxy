## Objective

Add the four operational limit variables and validate them at startup. Like task 3, the values
are validated and stored; nothing acts on them yet — admission control, queueing, and budget
enforcement are out of scope for this story and belong to slices #15+.

| Variable | Default | Rule |
| --- | --- | --- |
| `PROXY_MAX_CONCURRENT_REQUESTS` | disabled | absent / blank / `0` disables; otherwise a positive safe integer |
| `PROXY_MAX_QUEUE_SIZE` | `32` | positive integer; `0` is fatal |
| `PROXY_QUEUE_TIMEOUT_SECONDS` | `30` | positive integer; `0` is fatal |
| `PROXY_SAFETY_MARGIN_PCT` | `5` | integer `0`–`50` inclusive; `51` is fatal |

## Requirements

1. `config.js` owns all four reads. `server.js` does no parsing of them.
2. Config shape: add **one** field to the object `parseConfig` returns, grouping all four, so no
   caller can read three defaults beside a half-configured concurrency ceiling:

   ```js
   limits: {
     maxConcurrentRequests: <number | null>,   // null = concurrency limiting disabled
     maxQueueSize: <number>,                   // 32 by default
     queueTimeoutSeconds: <number>,            // 30 by default
     safetyMarginPct: <number>,                // 5 by default
   }
   ```

   `maxConcurrentRequests` is the only nullable member. The existing keys
   `{ baseURL, host, apiKey, proxyToken, unconfigured, rateLimit }` all stay, unchanged.
3. **Every supplied value must be decimal digits** (`/^[0-9]+$/` after trimming) and a safe
   integer. Reuse the guard task 3 established (`readPositiveInteger`) — do not write a second
   one, and do not relax it to `Number()` coercion. So `1e3`, `0x10`, `+5`, `.5`, `1_000`, a
   30-digit run, and anything `Number.isSafeInteger` rejects are fatal, each naming the variable.
4. **`PROXY_SAFETY_MARGIN_PCT` is additionally capped at 50.** `0` is valid; `51` is fatal. The
   story's Gherkin scenario names 51 as the fatal case.
5. **The blank check precedes numeric parsing.** `Number("  ")` is `0`, so a whitespace-only
   value that reached the numeric guard would read as a supplied value. Check `?.trim()` first
   and treat blank as absent — for the three defaulted variables, absent means the default; for
   `PROXY_MAX_CONCURRENT_REQUESTS`, absent means disabled.
6. **`0` disables only `PROXY_MAX_CONCURRENT_REQUESTS`, and is fatal for the queue size and the
   queue timeout.** The story table gives the concurrency variable an explicit
   "absent/blank/`0` disables" carve-out and gives the queue variables none, so `0` is fatal for
   `PROXY_MAX_QUEUE_SIZE` and `PROXY_QUEUE_TIMEOUT_SECONDS`. It is **not** fatal for
   `PROXY_SAFETY_MARGIN_PCT`, whose `0` is the low end of its `0`–`50` range — see requirement 4.

   > **Corrected after review (2026-09-30).** This requirement originally read "`0` is fatal for
   > them", where "them" meant all three remaining variables. That contradicted requirement 4,
   > the table at the top of this brief, the pinned decision in `specs/state.yaml`, test areas 3
   > and 7, and the story's own Gherkin scenario, all of which make `0` valid for the margin. The
   > implementer followed requirement 4 and declared the deviation; the reviewer and the orchestrator
   > both confirmed that was the right resolution. Left in place as written the requirement would
   > have made this brief's own required tests unpassable.
7. **Do NOT give `PROXY_QUEUE_TIMEOUT_SECONDS` the lenient `readSeconds` treatment.** It is a new
   operational variable, not one of the two existing timeout variables
   (`UPSTREAM_CONNECT_TIMEOUT_SECONDS` / `UPSTREAM_IDLE_TIMEOUT_SECONDS`). Do not touch
   `readSeconds` itself. Task 7's ADR records that contrast.
8. Do **not** add any other variable. Tasks 5 and 6 add the rest.

### Decisions already made — implement them, do not re-open them

These were recorded in `specs/state.yaml` before this task was dispatched. Rationale is there;
do not re-litigate it in code comments, and do not choose differently in the tests.

- **`0` is fatal** for `PROXY_MAX_QUEUE_SIZE` and `PROXY_QUEUE_TIMEOUT_SECONDS`. A queue size of
  zero or a zero-second wait silently turns queueing into immediate rejection — a limit that
  appears to exist and does not.
- **`PROXY_SAFETY_MARGIN_PCT` accepts `0`** and rejects `51`. Pin both ends in a test.
- **One `limits` object**, not four top-level keys. Same reasoning as task 3's single `rateLimit`
  field.

## The tests

Add tests whose **names contain one of** `PROXY_MAX_CONCURRENT`, `PROXY_MAX_QUEUE`,
`PROXY_QUEUE_TIMEOUT`, or `PROXY_SAFETY_MARGIN` — the verify command selects on name pattern, so
this is required, not stylistic. Put them in their own `describe` block (e.g.
`describe("operational limit config")`); the pattern matches test names, and the describe title
does not need to match.

**Do not use the word `whitespace` in any test name.** Task 6's verify gate requires a passing
test whose name contains both `whitespace` and one of these four variables, because the bare
word already matches pre-existing tests and two from task 3. If task 4 uses it, task 6's gate
passes on task 4's work and task 6 becomes unfalsifiable. Use `blank` in the name instead; you
may still pass `"   "` as a value.

Two harness seams already exist and you need no new one:

- `runProxyOnce(envOverrides)` spawns `server.js` bare, collects `{ code, stderr }`. Use it for
  every fatal case. It inherits `process.env`, so pass a valid `NVIDIA_BASE_URL`
  (e.g. `https://example.com/v1`) plus `NVIDIA_API_KEY` / `PROXY_AUTH_TOKEN` — otherwise the
  process exits 1 for an unrelated reason and the assertion proves nothing.
- `withProxy(t, { proxyEnv })` starts a stub upstream and a proxy child. Use it for the cases
  that must **start**.

Cover at minimum:

1. All four absent → startup succeeds, `/health` 200 (today's behavior, unchanged).
2. All four blank (`""`, `"   "`, `" \t "`) → startup succeeds, `/health` 200.
3. All four supplied and valid, including boundary values (`PROXY_MAX_CONCURRENT_REQUESTS=1`,
   `PROXY_MAX_QUEUE_SIZE=1`, `PROXY_QUEUE_TIMEOUT_SECONDS=1`,
   `PROXY_SAFETY_MARGIN_PCT=0` and `=50`) → startup succeeds, `/health` 200.
4. `PROXY_MAX_CONCURRENT_REQUESTS` is `0` → startup succeeds. This is the one documented
   "zero disables" case; it must be pinned, not assumed.
5. `PROXY_MAX_CONCURRENT_REQUESTS="   "` → startup succeeds, same disable path as `0`.
6. Each of the four, given a non-blank invalid value, exits 1 **naming that variable**. At
   minimum `0`, `-1`, `1.5`, `abc`, an unsafe integer, and `1e3`.
7. `PROXY_SAFETY_MARGIN_PCT` outside `0`–`50` → exit 1 naming `PROXY_SAFETY_MARGIN_PCT`
   (`51` is the story's named case; `-1` comes from the generic rule).
8. **Validated, not applied:** `PROXY_MAX_CONCURRENT_REQUESTS=1` plus a tiny queue still proxies
   a request through normally — status 200 and exactly one upstream request received. A later
   slice that starts acting on these has to change this test deliberately. Task 3 has the
   equivalent test for the rate pair; mirror its shape.
