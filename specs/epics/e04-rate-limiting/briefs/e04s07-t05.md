## Requirements

### 1. Repeated cleanup sequence admits every request

Drive several terminal paths in sequence against one proxy child:

1. JSON response carrying usable usage;
2. no-body response (204);
3. upstream 429;
4. JSON response without usable usage (fallback answer).

Every request must be admitted, complete its terminal path, release admission, and leave the
proxy usable. The stub must receive exactly one upstream request per attempted client request.

Use a budget large enough that admission, not token exhaustion, decides the result. Also use a
one-slot concurrency ceiling when useful, so a leaked slot would block the next request.

### 2. Every terminal path in sequence releases each slot

With `PROXY_MAX_CONCURRENT_REQUESTS=1`, drive this sequence:

1. normal JSON body;
2. 204 no-body;
3. HEAD;
4. client disconnect.

After each terminal path, the next request must be admitted. This proves every path releases its
admission slot exactly once. The stub must receive exactly one upstream request per attempted
request.

Use a high token budget so budget rejection cannot mask a leaked slot. For the disconnect path,
use a stub that holds the first response until the client cancels, then allows later requests to
complete normally.

### 3. Reconciliation remains single-shot

Unit-level `createBudget` test:

- reserve one request;
- `reconcile(actual)` succeeds;
- `reconcile(other)` is a no-op;
- `reconciledCount` equals 1;
- `fallbackCount` equals 0.

### 4. Fallback counters never double-count

Unit-level `createBudget` test:

- reserve one request;
- call `reconcile(null)` twice;
- `fallbackCount` equals 1;
- `reconciledCount` equals 0;
- a later `reconcile(actual)` adds no outcome.

## Orchestrator decisions

### D1 — Sequential requests expose slot leaks

Each next request starts only after the previous terminal path settles. A one-slot ceiling turns a
leaked slot into deterministic rejection instead of relying on timing under concurrency.

### D2 — Budget headroom isolates admission behavior

Token limits stay high enough for every request. A 429 in this sequence proves budget behavior
without making later requests fail for token exhaustion.

### D3 — One upstream attempt per client request

The stub request count must equal the number of attempted client requests. Any extra attempt
would indicate retry or replay policy.

### D4 — Tests only

Task 5 expects no production change. If a test exposes a defect, stop and report it instead of
editing production files.
