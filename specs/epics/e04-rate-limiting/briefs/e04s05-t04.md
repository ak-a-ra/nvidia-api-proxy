## Orchestrator decisions (apply these; record any deviation in the report)

### D16 — the client still learns nothing about which budget bit

The 429 response stays the fixed generic body `{ "error": "Too many requests" }` with a positive
`Retry-After` header, for a model rejection exactly as for a global one. The reason
(`model_rpm`, `model_tpm`, `rpm`, `tpm`) is internal to the budget and never reaches the client, is
not logged, and does not change the response shape. The model ID from the request body is not
logged either.

### D17 — the e04s04 test is renamed and its model entry becomes rpm-only

The ledger's verify pattern for this task matches `per-model limits are enforced`, so the updated
test carries that name. The old name (`... are accepted and do not change global behavior`) stated
the opposite of what the test now asserts, and it is the story's own change (story §2, "MODIFIED:
The existing per-model-limits-accepted test").

Its model entry becomes `{ "nemotron": { "rpm": 1 } }`. The old entry was `{ "rpm": 1, "tpm": 1 }`,
which no longer works: the effective token limit of 1 is below the estimated cost of a chat
completion (requested output alone is 1024 tokens), so the **first** request would be rejected with
`model_tpm` instead of the second being rejected with `model_rpm`. An rpm-only entry leaves the
token dimension uncapped, which is what the story's "partial model entry" scenario describes.

### D18 — the `admitWithBudget` comment must drop two false claims

The current comment says the wait "is implemented in budget.wait() and is wired here by e04s05+".
Both halves are false: `budget.js` has no `wait()`, and e04s05 defers budget waiting to a later
story (story §6, "Budget waiting deferred to a later story"). The rewritten comment says what is
true: over budget is answered immediately with a 429 whose `Retry-After` comes from the window's
own oldest live reservation, and no wait exists — a wait would park the caller and its concurrency
slot for most of a minute.

Keep the rest of the block's reasoning (why a 429 beats a wait) and its voice.

### D19 — the ledger's verify command is vacuous; strengthen it as tasks 1-3 did

The ledger's task-4 verify greps for `^[[:space:]]*ok [0-9]+ -`, which matches the file-level
`ok 1 - server.test.js` line a no-match run still prints. Use the name-counting form:

```bash
out=$(node --test --test-reporter=tap --test-name-pattern 'per-model limits are enforced|model limits without global pair' server.test.js 2>&1); rc=$?; test "$rc" -eq 0 || { printf '%s\n' "$out"; exit "$rc"; }; n=$(printf '%s\n' "$out" | grep -cE '^[[:space:]]*ok [0-9]+ - .*(per-model limits are enforced|model limits without global pair)'); test "$n" -ge 2
```

Replace **only** task 4's `verify` string in `e04s05-tasks.yaml` with this, keep the row's
`status: failing` until it exits 0, and record the change in the report. Do not touch the other
rows and do not touch the story-level `status`.
