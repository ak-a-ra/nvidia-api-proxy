## Requirements (from the task ledger, task id 3)

1. When `cost.model` matches a key in the model windows map, check the model's RPM window (if it
   has one) and its TPM window (if it has one) **after** the global check passes tentatively but
   **before** the global windows are charged.
2. If the model rejects, return immediately with `reason: "model_rpm"` or `reason: "model_tpm"`, and
   a `Retry-After` derived from the model window's oldest reservation. The global windows are
   never charged.
3. If both global and model pass, charge both atomically.
4. A `cost.model` that is `null` or not in the map skips the model check entirely (global only).
5. Tests: model RPM limit enforced (configured model with rpm 2, third request rejected with
   `model_rpm`), atomic reservation (a model rejection does not charge the global — verify the
   global counter), unknown model falls through to global only, partial entry (rpm only, tpm
   uncapped).

## Orchestrator decisions (apply these; record any deviation in the report)

### D10 — a check and its charge are separable, and the charge uses the check's snapshot

Task 2 left one window implementation with a `reserve()` that checks and charges in a single call.
Atomicity across two windows needs them separated: the global window must be able to say "this
cost would be admitted" without charging it, and the same for the model window.

The invariant the split must preserve is the one `budget.js` already states: "the estimate and the
admitted-or-rejected decision are computed against the same pruned snapshot, so two concurrent
requests cannot both observe the last free token". So the charge must use the same `now` and the
same pruned state the check used.

The window's public shape is yours to choose — a `check` that returns a rejection or a commit
handle, a `check`/`charge` pair, a `probe` that returns a ticket — but these hold:

- No `await`, no promise, no timer, and no callback sits between a check and its charge. The whole
  decision is synchronous, so nothing can interleave between "the model window rejected" and "the
  global window is not charged".
- A window that passed its check is charged exactly once.
- A window that failed its check is charged never.
- The global gate's observable behavior is unchanged: the same rejection reasons (`rpm`, `tpm`),
  the same `Retry-After` derivation, the same "RPM counted once per admitted request", the same
  disabled-gate behavior. The e04s04 tests are the proof.

### D11 — the reason is mapped at the budget level

The window implementation may keep its own `"rpm"` / `"tpm"` reasons internally. The budget-level
`reserve()` maps a model window's rejection to `"model_rpm"` / `"model_tpm"` and leaves the global
window's rejection as `"rpm"` / `"tpm"`. The global spelling is already pinned by an existing test
(`the global budget is unchanged when model limits are configured` in `server.test.js`); do not
change it.

Within one window, the request dimension is checked before the token dimension, matching the
global window's existing order.

### D12 — the HTTP response is not touched, and the reason never reaches the client

The 429 body stays the fixed generic `{ "error": "Too many requests" }` with a positive
`Retry-After` header. The reason is an internal value of the budget; it is not logged, not
returned to the client, and does not change the response shape. Task 3 does not touch
`server.js` — task 4 wires the model limits into the request path and covers the HTTP end to end.

### D13 — the model windows' closed flag is defense in depth, and stays

`close()` closes the global gate and every model window. The global gate refuses first, so a
reservation after `close()` is refused with `reason: "closed"` without ever reaching a model
window. The per-window flag is therefore not independently observable through the public API. Do
not contort the design to make it observable, and do not delete it: it is part of the one shared
window implementation, and the global window's use of the same flag is observable and tested.

Say in the report that this is unobservable, so the next reader does not mistake it for a covered
path.

### D14 — the model lookup is exact and never consults a prototype

The lookup is an exact own-property lookup of `cost.model` in the null-prototype model map. No
trimming, no case-folding, no normalization — the same rule the estimator applies (task 1) and the
same rule `config.js` applies when it stores the keys.

`cost.model === null` means there is no lookup at all. A model ID that is not in the map is
governed by the global budget alone.

A model ID of `"__proto__"` is an ordinary key here, not a prototype hazard: the map is
null-prototype, so the entry is stored, found, and enforced. Pin that with a test.

### D15 — the ledger's verify command is vacuous; strengthen it as tasks 1 and 2 did

The ledger's task-3 verify greps for `^[[:space:]]*ok [0-9]+ -`, which matches the file-level
`ok 1 - server.test.js` line a no-match run still prints. Use the name-counting form:


## Implementation notes

- The check order is fixed: global first, then the model window when the cost names a configured
  model. If the global rejects, return the global rejection without consulting the model. The
  story's §5 step 3 says the same.
- The model window is looked up only when `cost.model` is a non-null string. A `null` model skips
  the model check entirely.
- A model window with no window for a dimension does not check that dimension, and does not track
  it.
- The `Retry-After` for a model rejection comes from the model window's own oldest live
  reservation for the rejected dimension, exactly as the global window derives its own.
- Keep the module's comment voice: explain the constraint, not the mechanics. The comments must
  explain why the charge happens only after both checks passed, and why a rejected request must
  not touch the global window.
