# Task brief — e03s01 / tasks 1-5: opt-in per-request logging via `PROXY_LOG_REQUESTS`

> Source of requirements: `specs/epics/e03-request-logging/e03s01-tasks.yaml` tasks 1-5,
> `specs/epics/e03-request-logging/e03s01-opt-in-request-logging.md` §1-§19, plus
> `AGENTS.md` and `docs/adr/0002-config-operational-fail-fast.md`. Where this brief and the
> story disagree, the story wins and the deviation is reported — do not silently pick one.

## Objective

One JSON log line per request on stdout, gated by `PROXY_LOG_REQUESTS`, off by default. The
line carries method, path, status, duration. It must never carry a credential, a body, or an
upstream hostname, and logging must never change a response or throw into the request path.

Base state: branch `feat/e03-opt-in-request-logging` off merged `main` (`e69fa8f`), suite green
at **85 passing**.

## Two conflicts you must resolve deliberately

**1. `plans/05-opt-in-request-logging.md` contradicts the story. The story wins.**

The old plan says the format is `[req] POST /v1/models 200 1234ms` and suggests logging at the
end of the request handler. The story says the format is a JSON line and requires logging on
response **close**. Emit JSON:

```json
{"ts":"...","method":"POST","path":"/v1/chat/completions","status":502,"ms":1204}
```

Report this deviation explicitly. Do not update `plans/05` — it is a dated historical record
and its own header marks it superseded.

**2. `PROXY_LOG_REQUESTS` is config, and `config.js` now owns all configuration parsing.**

That extraction landed in e04s01 (merged `e69fa8f`, just now). So:

- Parse `PROXY_LOG_REQUESTS` in `config.js`, not `server.js`. `server.js` reads the parsed
  value from the config object.
- Follow the existing pattern: a blank value means absent, and the truthy set is whatever you
  document. The story's §9 says "any non-blank non-`0`/`false` value enables logging" — be
  deliberate here and say what you chose in a comment. Note the tension with the *other*
  operational variables in `config.js`, which are all decimal-digits-only booleans-by-absence
  (`Boolean(raw?.trim())`) and never silently reinterpret an operator's text. A truthy-string
  match like `/^(1|true|yes|on)$/i` is stricter and safer: `PROXY_LOG_REQUESTS=maybe` enabling
  logging is a coin flip, whereas `PROXY_LOG_REQUESTS=maybe` disabling it is the operator
  getting what a typo'd truthy string usually gets. **Prefer the strict truthy set** and
  document why, in the same spirit as ADR 0002's "a silently reinterpreted value is the
  failure this story exists to prevent."
- **This variable must be fatal-on-invalid, or explicitly documented as not.** ADR 0002 states
  the regime: operational variables fail fast, and a silently-defaulted limit is a budget that
  appears to exist and does not. A boolean flag is the weakest case — decide, record the
  decision in `specs/state.yaml`, and make it consistent with whatever you do. If you choose
  lenient, say so plainly in the comment and in the state decision; do not leave it implicit.
- **Add `PROXY_LOG_REQUESTS` to the `CONFIG_ENV_VARS` list in `server.test.js` in the same
  commit.** That list is what makes the suite hermetic against ambient env, and it is
  documentation-enforced: a new operational variable that does not join it silently reinherits
  ambient values and breaks the suite for whoever has one exported. `AGENTS.md` now requires
  this. Also `PORT`, the base URL, the two credentials, and the two timeouts are already in
  there — follow the existing shape.

## Requirements

1. **Off by default and indistinguishable.** Unset, blank, and falsy produce no output, no
   listener, no measurable overhead. The pre-existing suite must pass unchanged.

2. **One line per request, covering every branch.** `/health`, local 401/404/503, and proxied
   responses all log — those are exactly what debugging needs. §11: `/health` is **not**
   special-cased out.

3. **Log on response `close`, not at the end of the handler.** §12: a streaming response has
   no meaningful duration until it finishes, and §19 warns that writing inside the `pipeline`
   callback can fire before the response finishes. Register the listener only when logging is
   enabled, so the disabled path costs nothing — and so the SIGTERM test, which is
   timing-sensitive, does not gain per-request listeners.

4. **Elapsed time starts when the request arrives**, not when the listener registers.

5. **`try`/`catch` around the write.** §12 and §11: `console.log` to a closed or full stdout
   can throw, and a write failure must be swallowed so the request path is unaffected. The
   catch must be non-empty in intent — do not write an empty `catch {}`.

6. **Never log a secret.** Only method, path (including query string — the story's own example
   shows the path, and the path is operator-visible already), status, and duration. **No
   headers, no bodies, no `authorization` value, no API key, no proxy token, no upstream
   host:port.** This is task 4 and it is P0 — see the tests below.

7. **A response that never completes still leaves the process healthy.** If the upstream
   aborts mid-stream and the response is destroyed, the `close` listener must not throw or emit
   a malformed line. Decide what status to record in that case (`0`? `-`? the last known
   status?) and document it — the plan's older text used `-` for an errored stream.

8. **Streaming bytes stay byte-identical with logging on.** Compare the streamed body with
   logging on and off for the `sse` stub mode. This is task 3 and it is the requirement that
   proves you logged on close rather than mid-stream.

## The tests

Append a new `describe("request logging")` block. `server.test.js` must be **additive only**
for existing blocks — zero deletions, zero modifications, zero reorderings. Task 11's harness
change already touched the two spawn helpers, so reuse `runProxyOnce` and `withProxy` as they
now are; pass `undefined` for "absent" since `withProxy` merges over `process.env`.

**The harness gap you must solve first.** The child is spawned with `stdio` ignoring stdout
(see `startProxyServer`), so you cannot assert on log output as the suite stands. Task 4 is
worthless without it: "no secret in the log" cannot be tested against a log you cannot read.
Pipe the child's stdout when the test needs it, collect the chunks, and expose them on the
handle. Do not regress the default path — most tests want stdout ignored for speed. If piping
turns out to be genuinely invasive, say so and report it rather than shipping a weaker
assertion silently.

Required coverage:

1. **Off by default** — unset, blank, `"0"`, `"false"` produce **zero** bytes on stdout.
2. **On** — one line per request, and it parses as JSON with the expected `method`, `path`,
   `status`, and `ms` present and of the right type.
3. **`/health` is logged** when enabled.
4. **Local rejections are logged** — 401 (bad token) and 404 (bare `/v1`).
5. **Upstream failure is logged** with status 502, and the line must not name the upstream
   host, the DNS name, or the URL. §13 and the existing "error responses never leak internals"
   invariant.
6. **No secrets, ever** (task 4, P0). Assert the collected output does **not** contain: the
   proxy token, the API key, any `authorization` header value, the request body, or the
   upstream host:port. Cover a normal request, an unauthorized one, and a failing one.
7. **Streaming** (task 3) — the `sse` stub mode: the log line appears when the stream closes,
   not before, and the received bytes are byte-identical to the logging-off case.
8. **Logging on changes no response** (task 5) — same status, same body, same headers with
   logging on and off, for a proxied request and for a rejected one.
9. **A throw from the log write cannot reach the response path** (§11) — prove it, e.g. by
   making stdout unwritable or by stubbing `console.log` to throw, and showing the request
   still succeeds. If you cannot provoke a throw from the harness, say so explicitly rather
   than claiming the invariant is tested.

**Prove the gate is a gate.** At least two mutations, each reverted, each reported in both
directions: (a) log on `finish` instead of `close`, and (b) include the `authorization` header
or the request body in the line. Show which test catches each. A mutation no test catches is a
coverage hole — report it, do not hide it.
